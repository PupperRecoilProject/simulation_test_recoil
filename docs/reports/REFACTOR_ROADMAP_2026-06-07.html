② 各階段細節

P0 · 地基整理 已完成

風險 低 · T01 / T02 批次
  • 稽核三件（死碼 / config / 依賴）+ 韌體盤點 + 後座力斷線深查報告。
  • pytest 地基（13 passed）、工作區根 README。
  • 後座力接線修復、影像伺服器移除、後座力旗標改正向命名——全已併 main。
  • terrain_cache 久跑實測（T03-1）：確認無上限成長、但記憶體小、卡頓另有真因。

P1 · 機械式清理 建議下一步

風險 低 · 不動邏輯、可機械式提交、易回退 · 可與 P2 並行
  • print→log：滿地 print("✅…") 換成 log（順帶根治 cp950 啟動崩潰的殘餘風險）。純機械式、單獨提交。
  • 版本註解 / 歷史萃取：把 【vX.X.X】 行內註解萃取成一份版本歷史文件後刪除（決策 7）。
  • 死碼移除：依 AUDIT 報告清孤兒（已刪 tree_demo_server；其餘如 README 失效引用、test/ 混入的非測試腳本移 tools/）。
  • requirements.txt：依依賴稽核產生（剔 scipy、補 glfw、psutil 視需要）。

P2 · 正確性 / 效能硬化

風險 中 · 動到併發與核心狀態，每項配回歸測試
  • 中央鎖改分層（決策 4 / C4-1）：公開方法自鎖、私有 _xxx_locked 假定持鎖；根治非重入鎖自我死鎖風險。
  • terrain_cache LRU 上界（決策 5 / C5-1）：架構衛生（成長無上限屬實）。優先級下修——實測證明不是卡頓主因。
  • 查卡頓真因 C5-4：每次網格滑動重跑 25 個 generator + 重填 501×501 hfield + 同步，疑為「久跑超卡」來源；用真實物理+渲染情境量測。
  • data_capture_buffer 上限（C5-2）、時鐘分流（決策 2：sim 綁模擬時鐘、硬體綁牆鐘的軟體部分）。

P3 · headless 核心 API + Typer CLI

風險 中 · 需要 P2 的穩定核心；NiceGUI 暫留為過渡客戶端
  • 把模擬/控制邏輯抽成無 UI 依賴的核心 API（現況 run loop 與視窗/渲染耦合，headless 只走 mock 無真物理——這正是要解的）。
  • 用 Typer 寫薄 CLI 客戶端（PowerShell 跑），驅動核心 API。
  • NiceGUI 與 CLI 並存一段，核心邏輯只有一份。

P4 · 前端汰換

風險 高（大改） · 嚴格在 P3 之後
  • CLI 穩定後逐步棄用 NiceGUI，再選新前端（大主題，另議）。

③ 優先序速查

順位項目風險依賴為什麼這個順位
1P1 print→log / 死碼 / requirements低無零風險、立即降噪，讓後續 diff 乾淨
2P2 鎖分層中無併發正確性是物理系統安全底線，越早越好
3P2 查卡頓真因 C5-4低無實測導向；先量再改，避免修錯地方（LRU）
4P2 LRU / buffer / 時鐘中C5-4 結論確認真因後一起做效能類
5P3 核心 API + CLI中P2需要穩定核心才好抽離
6P4 前端汰換高P3CLI 成熟後才動 GUI
需要你定案的取捨：
  • P1 與 P2 要並行還是串行？（並行快、但 diff 交錯；串行乾淨、但慢）
  • terrain_cache LRU 既然非卡頓主因，仍要在 P2 做，還是降到 P3 之後當純衛生項？
  • 下一步要先動哪個——我建議 P1 的 print→log + 死碼（最安全、立即見效）。
